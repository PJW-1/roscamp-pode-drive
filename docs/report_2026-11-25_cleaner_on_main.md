## 1. 결론

- 청소 브랜치 다섯을 합쳤다. 충돌 7곳은 모두 양쪽 기능을 살려 풀었다. 합친 뒤 고친 것은 둘이다. plan_split 비교 파라미터 파일에 청소 키를 더했고, 새 지도로 `coverage_v7.yaml`을 다시 만들었다.
- **새 지도에서 v7 청소 경로가 바뀌었다.** 셀과 줄이 7셀 16줄에서 8셀 17줄로 늘었다. 한 바퀴는 104.8 s에서 116.8 s가 되었고, HALL 바닥 커버율은 63.4 %에서 67.5 %로 올랐다. d2는 그대로다.
- **새 지도에서는 기본값 판이 서로 막힌다.** v7 운반 2대와 청소 1대를 돌리면 seed 1, 2, 5에서 90 s 동안 관제 사건이 없다. 옛 지도에서는 0/5였고, 지금은 3/5판이 운반 주문을 끝내지 못한다. 막힌 꼴은 옛 기록 4-5절과 같다. 청소 로봇이 돌아오는 다리(back)에서 Q1을 쥐고 있고, 운반 로봇은 Q2에서 Q1을 기다린다. 옛 지도에서는 r4_off·ahead05·r3_only에서만 생기던 막힘이 이제 기본값에서도 생긴다. 4-6(운반 로봇에게 비키기)이 없어서 생기는 일이다.
- 그래서 `sim/fake_robots/test/test_world_cleaner.py::test_transport_orders_still_finish`(v7, seed 1)가 실패한다. 이 시험은 고치지 않았다. 아래 5절에서 사용자가 정한다.
- 바뀐 것은 거의 모두 지도 때문이다. 옛 청소 코드에 새 지도만 넣어 재 보니 v7 표가 새 코드와 같았다. r3_only 한 줄만 조금 다르다. 옛 코드와 옛 지도로 다시 돌리면 옛 기록 표가 그대로 나온다(결정적).
- 시험: fleet_core 전체 `1534 passed, 7 xfailed`. tools 청소 시험은 `16 passed`, pode_follow_wall은 `40 tests, 0 failures`다. fake_robots 청소 시험은 `1 failed, 7 passed`다.

## 4. 바뀐 결론

1. **"기본값은 막힘 없이 주문을 끝낸다"가 깨졌다.** 옛 지도의 default는 5/5판 모두 주문을 끝냈다. 새 지도에서는 2/5판만 끝낸다. 막힌 꼴은 모두 같다. 청소 로봇이 돌아오는 다리에서 Q1을 쥐고, 운반 로봇은 Q2에서 Q1을 기다린다. 옛 기록 4-5절에서 "4-6이 없어서 생긴다"고 본 꼴이다. 그래서 4-6(비키기)은 이제 R2·R4 조건을 바꿀 때만이 아니라 **기본값에서도 먼저 필요하다.**
2. **`clean_conflict_reach_m` 0.15 권장은 근거를 잃었다.** 옛 권장의 근거는 "막힘·새 위반·지연 증가가 없는 유일한 조건"이었다. 새 지도에서 reach015는 2/5판이 막히고, 덮은 비율은 0.552로 기본값보다 0.010 높을 뿐이다. 지연 평균은 22.0 s로 기본값 8.3 s보다 크다.
3. **path 미룸이 커졌다.** 혼자 판에서 22번이던 것이 50번이 되었고, seed 3에서는 다른 로봇 없이도 줄 16을 path 미룸 4번으로 포기했다. 옛 기록 결정 2(path 미룸 고치기)는 "작다"가 아니게 되었다.
4. **ahead10이 가장 좋아 보이지만 기본값으로 쓸 수 없다.** 덮은 비율 0.768, 막힘 없음, 못 끝낸 판 1이다. 그러나 청소 로봇이 든 위반이 9건 있다. 남이 쥔 지점에 청소 로봇이 서는 I8류다(옛 기록 4-6절과 같은 위험).
5. d2 결론(R2·R4 때문에 0/9, r3_only면 5~9/9)은 그대로다.
6. 청소 경로 계획(커버리지)과 FollowWall, 측정 도구(합성 bag)의 결론은 바뀌지 않았다. 모든 경로는 계속 0.093 m 기준을 지킨다.

1. **`test_world_cleaner.py::test_transport_orders_still_finish`(v7 seed 1) 실패를 어떻게 둘지.** 권장: 시험은 그대로 두고 4-6(비키기)을 다음 일로 한다. 이 시험은 지금 결함(막힘)을 바르게 잡고 있다. xfail로 돌리면 기준을 낮추는 것이라 하지 않았다.
2. **옛 남은 결정이 바뀌는지:**
   - 기본값 0.15로 바꾸기(defer 결정 1): 새 수치로는 근거가 없다. 권장: 바꾸지 않는다.
   - path 미룸 고치기(defer 결정 2): 혼자 판에서도 줄을 포기한다. 권장: 단계 3 첫 일로 올린다.
   - 4-6 먼저 하고 다시 재기(defer 결정 3): 이제 기본값부터 막히므로 더 급하다. 권장: 그대로, 우선순위를 올린다.
   - ahead·off 방식(defer 결정 4): ahead10의 청소 위반 9건으로 권장은 그대로다(실험 조건으로만).
   - Q15(쉼), Q16(우회 여유): 바뀌는 근거 없음.
3. **청소 goal의 결과 유실 처리(합친 뒤 드러난 차이).** main의 IR-62는 운반 goal의 결과를 잃으면 결과 모름으로 두고 점유를 쥔 채 상태 보고나 기한으로 정한다. 청소 쪽 `_clean_lost`(`traffic/zone/cleaning.py:533`)는 예전 규칙대로 goal을 지우고 몸 둘레 밖의 지점을 놓는다. 그러면 다음 걸음에 같은 다리를 다시 보낸다. 로봇이 옛 goal을 계속 가고 있을 수 있어 놓은 지점을 운반 로봇이 잡을 수 있다(Codex 검수 지적, 코드로 확인함). 합치기 범위 밖이라 고치지 않았다. 권장: 청소 goal도 IR-62처럼 결과 모름으로 둔다. 4-9(STOP 뒤 이어 하기)의 남은 결함 두 건과 함께 고친다.
4. 청소 브랜치를 main에 합치는 시점은 여전히 사용자 결정이다.
